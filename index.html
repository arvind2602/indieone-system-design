1. Executive Summary

System Purpose: indieOne is a multi-region investment super-app that lets users buy European/US ETFs through a regulated broker pipeline and participate in prediction markets through Polymarket — from a single Flutter client, with jurisdiction-aware feature gating.

Scope of v1:

  • ETF investing: onboarding → KYC → fiat deposit → market/limit orders via Alpaca + European ETF provider → positions & P&L
  • Prediction markets: Trust Wallet connect → 0x on-ramp/swap → USDC funding on Polymarket → trade → withdrawal
  • Region policy: prediction-market module enabled/disabled per jurisdiction (India = disabled), enforced server-side

Scale (v1 assumptions):

Dimension v1 Target v10 Target
Registered users 50k 2M
DAU 5k 300k
API requests/day 2M 400M
Market-data ticks/sec 500 25k
Peak concurrent WS clients 2k 100k

Key Challenges:

  1. Jurisdictional correctness — the prediction-market module must be provably unavailable in India while everything else works.
  2. Two incompatible money domains — fiat securities (Alpaca/EU provider custody) vs on-chain USDC (self-custody via Trust Wallet), unified in one UX without taking custody of either.
  3. Partner dependency blast radius — KYC vendor, Alpaca, Polymarket, payment gateways are all external; the design must degrade gracefully, never silently.
  4. Regulatory auditability — every order, gate decision, and KYC transition must be reconstructable after the fact.

2. Requirements

2.1 Functional Requirements

Identity & Onboarding

  • FR-1: Email/phone + OTP signup, with optional WalletConnect (Trust Wallet) link
  • FR-2: Multi-step KYC (document upload, liveness, AML screening) with vendor-agnostic adapter
  • FR-3: KYC state machine: draft → submitted → in_review → approved | rejected | rework
  • FR-4: Jurisdiction derivation at KYC time (document country + declared residence + IP signals) → stored, immutable-with-audit on the user record

Investing (ETF)

  • FR-5: Instrument search/browse over the European provider's catalog + Alpaca tradable universe
  • FR-6: Market/limit orders, order status stream (accepted → routed → partially_filled → filled | cancelled | rejected)
  • FR-7: Positions, avg cost, unrealized P&L, corporate-action-aware units
  • FR-8: Fiat deposit/withdrawal through payment provider → broker account
  • FR-9: Trade confirmations & periodic statements (PDF) generation

Prediction Market

  • FR-10: Trust Wallet connect (WalletConnect v2), balance read, 0x swap quote/execute for on-ramping to USDC
  • FR-11: Polymarket market discovery (CLOB API), order placement, position & P&L read, settlement history
  • FR-12: Feature availability strictly derived from JurisdictionPolicy — server-enforced, client-rendered

Platform

  • FR-13: Push/email/WhatsApp notifications for fills, KYC transitions, withdrawals
  • FR-14: Admin console: KYC review queue, account freeze, jurisdiction override (dual-control), feature-flag management
  • FR-15: Idempotent webhook ingestion from Alpaca, Polymarket, KYC vendor, payment providers
  • FR-16: Daily reconciliation across Alpaca, EU provider, Polymarket, and payment providers

3.1 Gate Enforcement (defense in depth)

Why server-side: hiding a tab in Flutter is cosmetic. A user on a VPN with a patched client could still hit the API. The gateway check is the compliance boundary; the UI is courtesy.

Override path: jurisdiction can only be changed by admin dual-control with reason codes, and every change writes an immutable audit_log row.

5. High-Level Architecture

Layered view: edge → BFF → core services → data → partners.

5.1 Why this shape

  • One gateway, one gate. Jurisdiction enforcement is a single chokepoint, not 14 scattered if statements.
  • Node as BFF, Go as core. Node/Express absorbs the messy, chatty, schema-volatile work (aggregation for Flutter, WS fan-out, webhook wrangling). Go owns everything where correctness and latency matter: orders, positions, payments orchestration.
  • Outbox, not dual-write. Any service that writes to Postgres and emits an event writes an outbox_event row in the same transaction; a relay publishes to NATS. No lost or phantom events.
  • Partner adapters, not partner spaghetti. Each external system is reached through an adapter interface inside one service — swap Polymarket for another venue without touching the client.

9. Data Model

Core entities (Postgres). Money is stored as bigint minor units + explicit currency — never floats.

Notes

  • audit_log is append-only (no UPDATE/DELETE grants), partitioned monthly, retained 7 years.
  • webhook_event.external_event_id is the dedupe key — every partner retries, so processing is idempotent by construction.
  • policy_snapshot on USER freezes the exact policy the user was granted at KYC decision time; a later flag change doesn't retroactively alter their history.
  • KYC document binaries live in S3 with SSE-KMS; Postgres only holds metadata + a hash.

11. Order Execution Design (money path)

Invariants

  1. client_order_id is the idempotency key end-to-end (client → BFF → partner). Duplicate submits return the original order.
  2. Never write order state and emit an event in different transactions (outbox).
  3. On partner timeout, query — do not resubmit.
  4. Every price is guarded by a user-set collar (limit) or max slippage (market) captured at submit time.
  5. Funds reservation happens before routing; release on cancel/reject.

13. Scaling, Observability, Reliability

Scaling

  • BFF: stateless, HPA on CPU + WS connection count (target 10k conns/pod)
  • Go services: HPA on request rate; marketdata-svc scales on tick throughput
  • Postgres: primary for writes, 2 read replicas for reporting/positions; partition fills, audit_log, outbox_event by time
  • Redis: cluster mode for quotes; separate instance for sessions vs cache
  • WS: Redis pub/sub fan-out so any BFF pod can serve any user

Observability — OpenTelemetry traces → Tempo/Jaeger, metrics → Prometheus → Grafana, logs → Loki (dev: Vercel + Grafana Cloud free tier). Every request carries trace_id, surfaced to the user in error screens for support.

Signal Threshold Alert
API error rate > 1% / 5 min page
Order submit p95 > 500 ms / 10 min page
Webhook processing lag > 2 min page
Outbox unpublished > 100 rows / 1 min page
Reconciliation diff > 0 unresolved ticket + notify
Partner circuit open 3 failures / 30 s degrade gracefully (read-only banner)

Reliability patterns

  • Circuit breakers + retries with jittered backoff on every partner adapter
  • Graceful degradation: if market data dies → serve last quote with stale flag; if broker dies → block order entry, keep browsing
  • Nightly reconciliation-svc compares your DB vs Alpaca vs EU provider vs Polymarket vs payment providers; diffs land in an ops exception queue — never auto-correct money
  • Backups: PITR on Postgres (7 days), daily snapshots (35 days), cross-region copy; RTO 1 h / RPO 5 min
